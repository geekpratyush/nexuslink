NexusLink

One Console · Every Protocol · Zero Context Switching

One desktop workbench for the protocols an enterprise actually runs on — with a single credential vault, one set of environment variables and one searchable history across every one of them. Offline-first: no account, no telemetry, no cloud dependency.

What is inside

Twenty-six protocols, one set of habits

Learn the workbench once. Every client below shares the same vault, the same ${VAR} environments, the same history and the same safety rails.

HTTP & APIs

REST with collections and a runner, WebSocket, SSE, GraphQL, gRPC. Enterprise auth built in: OAuth 2.0 with PKCE, AWS SigV4, Digest, HMAC, NTLM, mTLS.

Databases

A JDBC workbench that generates the SQL your engine actually accepts, plus MongoDB with a Compass-class tree view, a mongosh-style shell, change streams and GridFS. Redis with a console that sends anything the server supports.

Messaging

Kafka with headers, tombstones, Avro decoding, consumer-group administration and replay. MQTT, RabbitMQ, JMS, IBM MQ, Solace, SQS/SNS, Pub/Sub and Service Bus.

Files & directories

A two-pane commander over SFTP, FTP, S3, Azure Blob, GCS and GridFS — with a transfer queue, directory compare and checksums. LDAP, SNMP and an SSH terminal.

One workbench

One encrypted vault, one set of environments, one searchable history and code generation — shared by every protocol rather than reinvented per tool.

Safe by default

Credentials are never displayed in the clear, destructive statements are previewed and confirmed, and bulk writes count what they would touch before they run.

Install

Run it straight from Artifactory

Download one launcher, put it anywhere, run it. On a machine where Maven is already set up — the usual case inside a company — there is nothing to configure: the launcher reads the repository and its credentials from ~/.m2/settings.xml. On the first run it fetches the application and caches it; every run after that starts from the local copy, offline. You need Java 21 or newer — nothing else.

nexuslink.shLinux and macOS nexuslink.batWindows — prompt or double-click nexuslink.ps1Windows — PowerShell (the .bat calls this)

On Windows keep nexuslink.bat and nexuslink.ps1 next to each other — the batch file hands over to the PowerShell script. On Linux and macOS make it executable first: chmod +x nexuslink.sh.

First run

# Linux / macOS
chmod +x nexuslink.sh
./nexuslink.sh

# Windows
nexuslink.bat

That is the whole thing. The launcher looks for the repository in this order: --repo on the command line, then NEXUSLINK_REPO_URL, then ~/.nexuslink/bootstrap.conf if your administrators ship one, and finally Maven's own settings.xml — the mirror that covers everything, or else the first repository a profile declares, with credentials taken from the matching <server>. If Maven can already reach your Artifactory, so can NexusLink.

Only if this machine has no Maven set-up do you need to point the launcher somewhere yourself: ./nexuslink.sh --repo https://artifactory.example.com/artifactory/libs-release, or export NEXUSLINK_REPO_URL once.

Everyday commands

nexuslink                      # run; downloads only if this version is not cached
nexuslink --version 1.2.0      # run a specific version (or RELEASE / LATEST)
nexuslink --offline            # never touch the network; run the newest cached build
nexuslink --update             # re-download this version over the cached copy
nexuslink --fresh              # clear the cache, then download and run
nexuslink --list               # show what is cached, with sizes
nexuslink --where              # print the jar that would run, and exit
nexuslink --local              # run the build publish.sh installed into ~/.m2
nexuslink --help               # the full usage text

Settings

VariableMeaning
NEXUSLINK_REPO_URLThe Maven repository to fetch from. Optional — without it the launcher reads ~/.m2/settings.xml.
NEXUSLINK_VERSIONRELEASE (default), LATEST, or an exact version
NEXUSLINK_USER / NEXUSLINK_TOKENRepository credentials, if it needs them. Optional — otherwise taken from the <server> in settings.xml.
NEXUSLINK_HOMEWhere the cache lives (default ~/.nexuslink). Set it to ./nexuslink-cache to keep everything in the current folder.
NEXUSLINK_JAVA_OPTSExtra JVM options, e.g. -Xmx2g
JAVA_HOMEThe JDK to run with, if not the one on PATH

Publishing it — for whoever maintains the build

./dist/publish.sh                 # build, install to ~/.m2, deploy if a repository is configured
./dist/publish.sh --local         # local only
./dist/publish.sh --deploy        # require a deploy; fail if none is configured
./dist/publish.sh --version 1.2.0 # set the release version first

Credentials live in ~/.m2/settings.xml under a <server> id, never on the command line — which is also how a CI agent supplies them. Full detail in DISTRIBUTION.md.

Contributing

Fork it, change it, open a pull request

The full guide is in CONTRIBUTING.md. The short version:

  1. Fork the repositoryUse the Fork button on the repository page. That gives you your own copy to push to — you do not need write access to the original.
  2. Clone your fork and add the original as upstream 
    git clone <your-fork-url> nexuslink
cd nexuslink
git remote add upstream <original-repository-url>
  3. Branch from an up-to-date main 
    git fetch upstream
git checkout -b feature/short-description upstream/main
  4. Build and test before you push 
    mvn -q verify          # the whole build, all modules
mvn -q -pl nexuslink-protocol-kafka test   # just the module you touched
    The default build needs no Docker and no network beyond dependencies — live integration tests are gated behind properties such as -DrunMongoIT=true.
  5. Commit in the project's voiceOne concern per commit; a subject line that says what changed and why, in plain words, no ticket-speak.
  6. Push and open the pull request 
    git push -u origin feature/short-description
    Open the PR against main of the original repository. Say what changed, why, and how you verified it; link any issue it closes.
  7. Keep it currentIf review takes a while, rebase rather than merge: git fetch upstream && git rebase upstream/main.

Troubleshooting

If something goes wrong

MessageWhat it means
no repository found in ~/.m2/settings.xmlThis machine has no Maven repository configured and no NEXUSLINK_REPO_URL. Pass --repo <url>, or ask for the bootstrap.conf.
checksum mismatchWhat arrived does not match the repository — usually a proxy interfering. Retry; if it persists, tell whoever maintains the repository. Nothing is cached.
… is unreachable — running the cached versionNot an error. The repository could not be reached — off the VPN, or down — so the launcher started the copy it already had.
nothing cached … --offlineThis machine has never run online. Run once with network access first.
Java N found, but … needs 21Install a newer JDK, or point JAVA_HOME at one you have.
Error in glXCreateNewContextNot an error. JavaFX could not get a hardware graphics context and fell back to software rendering; the app runs normally.
